1. Preserve first, synchronize second

The first useful command should answer four questions: what work exists here, where else it has been safely preserved, what can be synchronized without risking that work, and what needs reconciliation.

A successful Git push does not preserve dirty files, ignored data, a running database, or the keys needed to recover an encrypted backup.Backup, synchronization and reconciliation are separate operations. The system must remain useful without internet, without an AI subscription, and without every usual device being present.

The immediate aim is not a universal mesh. It is a trustworthy command that saves otherwise unprotected work and explains precisely what remains at risk.

2. Reuse the existing foundations

Frog already owns repository identity, discovery, workspace coordination, locks and SSH federation. Rebekah supplies runtime integration and an authenticated gateway. Dash already exchanges private instance views, including Daily Agenda. These should become adapters, not competing systems.

3. A Rust workspace with a reusable core

Create tabenius/rebsync, private initially, with exactly two application crates from day one. Organization ownership at RAGBAZ/rebsync is an alternative, not a reason to create duplicate projects.

rebsync/
├── Cargo.toml
├── Cargo.lock
├── crates/
│   ├── rebsync-core/
│   │   └── src/
│   │       ├── config / inventory / planning
│   │       ├── execution / git / datasets
│   │       ├── peers / transports
│   │       └── reconciliation / journal
│   └── rebsync-cli/
│       └── src/main.rs
├── tests/
└── examples/

The core owns configuration loading, discovery, subprocesses, files, API calls, policy, planning, execution and structured events. It knows nothing about terminal rendering or interactive prompts.

The clap-based CLI parses terminal input, passes explicit overrides, displays results and maps outcomes to exit codes. A later Tauri or Dioxus interface imports the same core.

Use ordinary tools first: Git, GitHub CLI, SSH and established backup utilities. Pass arguments directly rather than interpolating shell commands; construct explicit pipelines only when necessary.

Keep storage providers behind a narrow Rebsync-owned interface inside the core. Client adapters, incoming server protocols and synchronization policy are separate responsibilities. The experimental storage comparison is a standalone, unpublished workspace under evaluations/storage/; it adds no dependency or third crate to the production workspace.

4. Predictable configuration

Support TOML and YAML. Configuration precedence is built-in defaults, user configuration, Rebekah-home configuration, an explicit configuration file, then CLI options.

rebsync                  # rebekah_home defaults to $HOME
rebsync .                # use this directory instead
rebsync . --dry-run
rebsync config explain   # effective configuration and origins

Discover user configuration under $XDG_CONFIG_HOME/rebsync/ and home configuration as rebsync.toml or rebsync.yaml. Competing formats at the same layer are an error. Reject unknown keys. Replace lists by default rather than silently concatenating them.

5. Safe Git exchange

inventory → preserve → fetch → plan
          → synchronize → reconcile → verify → summarize

Use Frog discovery where available, with filesystem discovery as a fallback. Account for nested repositories, linked worktrees, .git files, bare repositories, detached HEADs and naming collisions.

Before moving branches, preserve relevant refs and commit IDs, uncommitted tracked changes, selected untracked files and needed dataset state. Never automatically commit dirty work into shared or public history. Preserve it privately and encrypted.

  1. Identify trusted read sources and permitted write destinations.
  2. Fetch sources independently. A failed source must not invalidate successful fetches from another.
  3. Preserve divergent branch tips before reconciliation.
  4. Automatically fast-forward only when safe.
  5. Push eligible local branches using ordinary, non-forced pushes.
  6. Record rejected pushes, divergence, protected branches and missing permissions explicitly.

Default prohibitions: no force pushes, deletion propagation, automatic stash/pop cycle, operator working-tree rewrites, or git push --mirror against shared repositories. Do not assume a default branch is named main; do not merge every feature branch into it.

Fetch and preserve remote-only branches. Publishing them elsewhere requires a mapping, not accidental conflation of branches sharing a name.

Creating missing GitHub repositories

Distinguish an owned project lacking GitHub storage, a forkable GitHub upstream, and an independent repository originating on Kali or another host. Retain provenance and existing remotes. Never replace origin blindly.

Require approval of first-run destination mappings and visibility. Naming collisions and possible private upstream content require review.

6. An exact, restartable journal

Write a collision-safe JSONL journal directly under the selected Rebekah home, with UTC timestamps:

rebsync_2026-11-13_172405.jsonl
.rebekah/rebsync/          # separate resumable state

Each event records run and action IDs, repository or dataset identity, peer and transport, planned action, result, redacted executable arguments, timestamps, exit status, before/after refs or digests, verification and skip reasons.

Write intent before mutation and completion afterward. Stop new mutations if journaling fails. Redact secrets and avoid logging file contents. Use per-repository locks, bounded retries, timeouts and stale-plan checks. An interrupted run must not look like a completed one.

7. OpenCode reconciliation, with limits

Enable reconciliation assistance by default. For divergence, create an isolated worktree and write rebekah-repo-reconcile-merge.md there, recording source refs, target, preserved tips, constraints and required tests.

Launch OpenCode only when available and permitted. Preserve the instructions and work when AI access is unavailable. Capture its outcome and independently inspect the resulting Git state.

A textual merge is not evidence of semantic correctness. Repository content is untrusted input, not authorization to alter synchronization policy.Allow preparation of reconciliation commits in isolation. Do not expose unrestricted backup credentials. Enforce permissions, execution and spending budgets. Default-branch publication needs configured checks and authorization; otherwise publish a review branch and handoff.

AI reconciliation must never be required for backup success.

8. A storage stack: filesystem, S3, R2 and restic

Storage saves bytes. Protocol adapters expose access. Rebsync decides what the bytes mean, where they should travel, and whether they are sufficiently protected. Build the lower stack early, before mesh networking or autonomous merging.

Rebsync orchestration
  Git · datasets · preservation · reconciliation · routing
                         │
              Storage interface + policies
                         │
          ┌──────────────┼────────────────┐
     Filesystem     S3 backend       REST backend
     USB / disk     AWS S3 / R2      restic REST server

Incoming clients
  restic REST API · S3 API subset · Rebsync peer API
                         │
              Authorization + quotas
                         │
                Storage interface

A node may act as a client, a server, or both. Serving a protocol and storing through a backend are independent capabilities. A phone might expose a restic REST endpoint backed by local storage, then relay completed backups to R2 when the internet returns.

R2 implements a subset of the S3 API. Prefer “S3-compatible endpoint, Rebsync object profile, tested against AWS S3 and R2” over claiming to reproduce Cloudflare’s entire service. See R2 S3 compatibility.Use one S3 client family with provider profiles for AWS S3, Cloudflare R2 and other compatible endpoints. Set endpoint, region, addressing, authentication and feature support explicitly; test each provider. R2 is not an ordinary Git remote and does not accept git push.

The existing command delegates encrypted backup to restic and can configure its S3 backend. That is not yet a native Rust S3 adapter or a storage server. Retain restic’s encryption, repository format and restore tooling rather than inventing cryptography or a backup format.

Storage milestone 1 · reliable objects and restic REST

OperationMinimum contract
PutObjectBounded-memory upload; atomic publication; declared durability; create-if-absent and conditional replacement where supported.
GetObjectStreaming and byte-range reads, with explicit integrity checks.
HeadObjectSize and relevant metadata without reading the entire object.
ListObjectsV2Correct raw-prefix, delimiter and continuation-token behavior; use V2 rather than legacy listing.
DeleteObjectAvailable internally but restricted by authorization and retention policy; no automatic cross-peer deletion propagation.

Distinguish not-found, forbidden, unavailable, corrupt and unsupported operations. Record consistency guarantees, checksums, limits and atomicity, not just method names. ETags are opaque validators, not universal content hashes. Do not emulate atomic create-if-absent with a separate HEAD followed by PUT.

A filesystem adapter must use a dedicated object namespace with safe key mapping. Arbitrary S3 keys are not safe filesystem paths. Handle traversal, symlinks, case sensitivity and file/directory collisions; publish temporary files atomically and synchronize files and directory entries before claiming local durability.

Bring restic REST API interoperability into this milestone, before a broad S3 server. Initially, a future rebsync serve may supervise the established rest-server; a native Rust adapter can follow. Repository-format compatibility is distinct from REST-protocol compatibility. Store encrypted repository objects opaquely.

Validate repository creation, config access, typed object lists, HEAD, byte ranges, writes, errors and API-version negotiation against real restic. Normal backup needs lock deletion. Append-only policy protects existing backup objects while allowing the narrowly authorized lock lifecycle; pruning remains a separate administrative operation. Do not expose a listener without authentication, namespace isolation, quotas and TLS or an authenticated encrypted tunnel.

Storage milestone 2 · resumable transfer and an S3 server profile

CreateMultipartUpload · UploadPart · CompleteMultipartUpload
AbortMultipartUpload  · ListParts  · ListMultipartUploads

Persist upload IDs and part receipts across process restarts. Validate part order and sizes, handle retry and uncertain completion safely, publish the completed object atomically, and expire abandoned uploads under explicit policy. Respect provider-specific part limits. Multipart is a transport mechanism, not a requirement that all Rebsync datasets use the same chunk format.

Implement an explicitly tested S3 wire profile: Signature Version 4 verification, HTTP/XML errors, ranges, conditional requests, pagination, supported addressing and required bucket probes such as HeadBucket. Return an explicit unsupported-operation error outside that profile. A client SDK or storage abstraction is not itself an S3 server.

Storage milestone 3 · authenticated capability discovery

Design the capability schema in milestone 1, then implement negotiation and discovery in milestone 3. Advertise software capability, currently available endpoints, caller authorization and storage guarantees separately. Report provider connections separately from incoming server protocols: “I can upload to R2” does not mean “I expose an S3 endpoint.”

Each protocol advertisement includes a version/profile, endpoint, client/server role, permitted operations and limits. A hop additionally advertises its Rebsync routing role. Keep anonymous discovery minimal; bind authenticated capability responses to an enrolled identity, check freshness, and verify compatibility with conformance tests and bounded probes. Self-description alone is not proof.

Independent recovery, not just successful transfer

A private S3 or R2 location should hold encrypted repository recovery material, dirty-work snapshots, consistent Frog backups, Daily Agenda editions, journals and recovery inventories. Validate each real endpoint through an off-machine restore. Passing a local filesystem probe is not evidence of cloud compatibility or protection against losing the laptop.

Use rclone where broad transport support helps, including a later Google Drive copy. Destructive bidirectional file synchronization is not the default backup policy.

  • Use bucket-scoped credentials and separate deletion privileges where practical.
  • Start with conservative retention and no automatic pruning.
  • Set storage, request and large-file budgets.
  • Keep recovery keys outside both the laptop and the backups they unlock.
  • Test retention locks before adopting their operational and cost consequences.

Dash can show status and coordinate authenticated exchanges. Its current bounded projections are not full backups. A Cloudflare Worker is not an environment where arbitrary Rust CLI subprocesses can be assumed to run.

9. Frog and Daily Agenda

Consistent task data

Do not casually copy an active SQLite file or merge database files. Obtain consistent backups on the authoritative host using SQLite’s backup mechanism. Keep offline snapshots read-only; queue offline changes as stable-ID operations and replay them through supported Frog contracts.

Conflict rules for independently edited tasks come later. Copying one database over another is not reconciliation.

Whole agenda editions

Synchronize snapshot.json, editorial.json and manifest.json as one verified edition. Preserve original source timestamps and last-known-good editions; receiving or rerendering an old edition must not make it look fresh.

Reuse Rebekah’s manifest validation and authenticated Dash connector. Do not create a public artifact directory as a shortcut.

10. Peers, sinks, sources and hops

A peer or node is an identified participant. A sink accepts authorized data; a source provides it. A hop can invoke its own local rebsync and participate in onward exchange.

Separate identity, address, capability, authority and trust. One peer may be reachable through a directory, SSH, HTTPS, object storage, LAN, Bluetooth or a future mesh address. A familiar Wi-Fi SSID is a discovery hint, not authentication.

DestinationFirst transport
GitHubGit over SSH/HTTPS
KaliExisting Tailscale SSH
USBExplicitly enrolled mounted directory
S3 / R2Encrypted object backup through provider-specific profiles
Restic REST peerAuthenticated REST protocol over TLS or encrypted tunnel
AndroidTermux-hosted Rust CLI over authenticated SSH, if supported
DashExisting HTTPS connector; sync endpoints later

Enroll USB devices using a stable identity and marker, not just a mount path. Never write to every removable drive automatically.

Later, negotiate a versioned manifest such as rebekah.peer.v0.1, verify pinned identities and restrict datasets and operations. A public-key filename alone does not authenticate a phone.

Store-and-forward needs deduplication, acknowledgements, quotas, expiry and hop limits. Advertise verified possession, not attempted uploads. Add Bluetooth, OSHI mesh, Plan 9 and other adapters after file and SSH exchange work reliably; inspect the actual bridge contracts first.

received → locally durable → verified → replicated upstream

A phone acknowledging local storage must not imply that R2 already has a copy. A cloud-backend profile is not a live cloud connection; an advertised feature is not permission to use it.

Never reconcile disconnected writable restic replicas by blindly merging object directories. Independent nodes start with separate repositories or coordinated consistent replicas. Copy snapshots through restic-aware operations when connected; do not pretend disconnected replicas share a functioning lock domain. Preserve pack/index/snapshot ordering and prevent conflicting pruning.

11. Delivery and proof

The application stages below remain the overall roadmap. The three storage milestones are a separate workstream feeding those stages, not a claim that application stages 1–3 have all shipped.

Test interrupted uploads, full disks, hostile filenames, malformed manifests, changed host keys, concurrent runs and clock skew from the beginning.

Storage acceptance additionally requires publication-time exclusion under competing writers, correct raw-prefix pagination, restart-resumable multipart, range restores with real restic, and provider-specific AWS S3/R2 tests. Do not infer any of these from successful client construction or a single-machine smoke test.

The first milestone

One command discovers your work, preserves otherwise-unprotected changes to an independent destination, safely exchanges eligible Git branches, and tells you exactly what remains unprotected or unresolved—even without internet or AI access.

Start with application stages 1–3 and storage milestone 1. Keep independent S3/R2 preservation ahead of autonomous merging. This gives immediate practical value without postponing the design needed for phones, removable media and intermittently connected Rebekah hops.

12. Rust storage evaluation

Evaluate Apache OpenDAL™ 0.59.5 and object_store 0.14.2 in an isolated workspace before selecting a production dependency. OpenDAL offers broader transport coverage and runtime capability metadata; object_store offers an object-focused contract, explicit create modes and lower-level multipart/pagination interfaces. Neither is a complete S3 server or restic REST server.

The initial probes exercise real temporary filesystem backends, not mocks: put/get/head, ranges, listing, deletion, staged publication, abort and competing create-if-absent writes. S3 and R2 builders use dummy credentials without making cloud requests. Results and decision gates are maintained in docs/STORAGE-EVALUATION.md and evaluations/storage/results/.

Selection remains provisional until the semantic probes and provider tests are evaluated. In particular, verify durability settings, capability flags versus actual exclusion behavior, raw-prefix listing versus directory semantics, and multipart restart recovery. Do not add either abstraction to the production crates simply because it compiles.
